## 3. Decisiones abiertas

1. **¿Qué es hoy el "favorito"?** En el código solo existe "Apuntar como candidato" (botón de texto en `src/components/LiveSearch.tsx`). Asumo que es ese. Confirmar.
2. **Proyecto de Supabase.** ¿Crear uno nuevo en la cuenta del usuario (plan gratuito, región UE) o usar uno existente?
3. **Acceso a datos.** Recomendado: tablas con RLS activado y **sin políticas para `anon` ni `authenticated`**. Todo acceso va por rutas de servidor (`src/app/api/...`) con la clave `service_role` solo en el servidor. Motivo: sin Supabase Auth, RLS no sabe qué usuario hace la petición; cerrar las tablas al cliente es la única forma de que "un usuario solo ve su grupo" se cumpla en serio. Alternativa: sesión firmada en cookie + políticas RLS que lean una cabecera; más compleja y no la recomiendo para el MVP.
4. **Hash de contraseñas.** Recomendado: `bcryptjs` en la ruta de servidor (no `pgcrypto` en cliente). Coste de trabajo bcrypt 10–12.
5. **Sesión tras entrar.** Recomendado: cookie `httpOnly`, `secure`, `sameSite=strict`, firmada (HMAC con secreto en variable de entorno), caducidad 12 h, ligada a `grupo_id` y `miembro_id`.

## 4. Modelo de datos (Supabase, Postgres)

```sql
create table grupos_cooperativos (
  id uuid primary key default gen_random_uuid(),
  nombre text not null check (char_length(nombre) between 2 and 120),
  slug text not null unique check (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  password_hash text not null,               -- bcrypt, nunca texto plano
  created_at timestamptz not null default now()
);

create table miembros (
  id uuid primary key default gen_random_uuid(),
  grupo_id uuid not null references grupos_cooperativos(id) on delete cascade,
  nombre text not null check (char_length(nombre) between 1 and 60),
  password_hash text not null,               -- bcrypt, nunca texto plano
  created_at timestamptz not null default now(),
  unique (grupo_id, nombre)
);

create table favoritos (
  id uuid primary key default gen_random_uuid(),
  miembro_id uuid not null references miembros(id) on delete cascade,
  oferta_id text not null,                   -- id del listado (fuente + id del anuncio)
  datos jsonb not null,                      -- solo: titulo, zona, precio, m2, url, fuente, tipo
  created_at timestamptz not null default now(),
  unique (miembro_id, oferta_id)
);

alter table grupos_cooperativos enable row level security;
alter table miembros enable row level security;
alter table favoritos enable row level security;
-- Sin políticas: anon y authenticated no pueden leer ni escribir. Solo service_role (servidor).
```

Notas:
- `favoritos.grupo_id` no hace falta: se llega al grupo por `miembro_id`. Menos datos duplicados.
- `datos` se limita en servidor a una lista blanca de campos. Nada de ingresos, bancos ni teléfonos.
- `unique (miembro_id, oferta_id)` evita duplicados al pulsar el corazón dos veces.

## 5. Flujo de acceso

1. **Entrar al grupo:** `slug` + contraseña de grupo → `POST /api/grupos/entrar` → cookie de sesión de grupo.
2. **Elegir miembro:** lista de miembros del grupo (solo nombres) → contraseña individual → `POST /api/miembros/entrar` → cookie de sesión de miembro.
3. **Ver favoritos:** `GET /api/favoritos?filtro=todos|mios` → cada favorito con el nombre de quien lo marcó.
4. **Alta de grupo:** `POST /api/grupos` (nombre, slug, contraseña de grupo, nombre y contraseña del primer miembro). Slug único; si existe, error genérico.

Límites: rate limit por IP en login (reutilizar el patrón de `src/lib/guards.ts`) para frenar fuerza bruta sobre contraseñas.

## 7. Minimización de datos y privacidad

Datos que se guardan en servidor:
- Grupo: nombre, slug, hash de contraseña, fecha.
- Miembro: nombre (solo nombre de pila o alias, sin apellidos), hash de contraseña, fecha.
- Favorito: id de la oferta, datos públicos del anuncio, fecha.

Datos que **no** se guardan en servidor: ingresos, deudas, datos bancarios, documentos, teléfonos, correos, direcciones de las personas.

Aviso de privacidad (texto a redactar y revisar): qué se guarda, para qué (identificar al grupo y sus favoritos), quién lo ve (solo miembros del grupo), dónde (Supabase, región UE), cuánto tiempo, y cómo borrar un miembro o un grupo. Enlace visible en la pantalla de alta y en el pie.

Pendiente de decidir: derecho de supresión. Propuesta: el administrador del grupo puede borrar el grupo entero (cascada), y cada miembro puede borrar su propia cuenta de miembro.
